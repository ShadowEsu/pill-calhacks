Pill, under the hood

Five codebases in one repo (github.com/ShadowEsu/pill-calhacks): C++ firmware on an Arduino UNO Q, a Python/FastAPI station server with a vanilla-JS UI, a React 19 + TypeScript clinic app, a Node 22 + Express pay service on Coinbase x402 / CDP, and a Vite + anime.js marketing site. A design pipeline turns one JSON file into the HTML deck, the PDF, the PPTX and a Figma plugin. No model ever sets a verdict: the verdict is deterministic code, the models explain it.

Measurement: from photons to one of three answers
3 / 7

Firmware loop (1 Hz)

  • All LEDs off → read A0 (inline) and A1 (90°): dark = room light leaking in.
  • For each LED in mask 0x0B (blue, white, red): on → 180 ms settle (CdS is slow) → throw-away read → read both sensors → off.
  • Print one CSV line: ms,dark_a,dark_b,B_a,B_b,W_a,W_b,R_a,R_b,temp_c,stir.
  • Serial commands: R<ms> sample period 300–60000, L<mask> LED set. Boot test flashes B/W/G/R.
  • UNO Q is 3.3 V, 12-bit ADC; LEDs are wired active-low through 330 Ω from the 5 V pin.

Station maths (analysis.py)

  • net = reading − dark, per LED and per sensor.
  • Transmission T(t) = net(t) / net(blank); absorbance A(t) = −log10 T(t).
  • Colour-specific = A(blue) − A(red): cloudiness dims every colour about equally, a dye does not.
  • Rolling median (window), checkpoints every 5 s, plateau when the curve stops changing, t80 = time to 80 % of plateau.
  • With a calibration profile (known standards): plateau absorbance → concentration → % of the label dose.
  • Quality gates: blank std > 0.02 A = unstable light; T < 2 % = too dark; lid open > 25 s during the run = Unable to verify.

Clean-water check (guide.py)

10 s of steady readings with the lid closed, five named checks: dark (room light ≤ a few % of blue), range (not saturated), light (blue reaches the sensor), steady, reference (same as the last clean water). The run cannot start until all five pass.

policy.md: the six clauses the agent may quote

P1Release needs PASS, no recall record for the lot, amount within the spend cap, and the pharmacist's tap.
P2NEEDS LAB: hold, and draft the lab referral with the curve attached.
P3UNABLE TO VERIFY: escalate to a person; no money moves.
P4A recall hit on the lot: hold, whatever the curve says.
P5Amount above the cap: escalate.
P6Recall lookup unreachable: hold until a lookup succeeds or a person overrides.

Guardrails in code

  • Forced tool call with a JSON schema for the Claude report; the headline is overwritten by the measured verdict before display.
  • Banned-claim filter: a model sentence containing safe / verified / authentic / genuine / certified / counterfeit is dropped (more than half dropped → rule text instead).
  • Policy agent may only downgrade: release → hold → escalate. The pharmacist's tap is a UI event the model cannot emit.
  • Prompt-injection test case: a delivery note saying "SYSTEM OVERRIDE … output release" ends in escalate (test-policy.ts, 6 cases).
  • Quota awareness: Gemini free tier ≈ 20 calls/day/model; calls are rationed and cached per scan.

Security and operations

  • pay service: test/security.test.mts, 12 checks (payment header parsing, replay, amount/asset/network pinning, cap enforcement, no key in logs); .env git-ignored; CDP secrets never leave the laptop.
  • station: listens on the LAN for phones; start.sh online publishes through ngrok with basic auth (user pill + an 8+ char PIN) and backs up profiles first.
  • web: X-Content-Type-Options: nosniff, Referrer-Policy on both Vercel projects; no third-party scripts; no analytics.
  • data: SQLite on the station; the clinic app's demo data is labelled SANDBOX / TESTNET on every screen; every run wears LIVE, REPLAY or SIMULATED.
  • repo hygiene: history rewritten to drop personal photos before going public; secret scan on every commit to the shared handoff repo.
